# S2.1 — Two front ends: the legacy shell and the Iapetus app

## In one line
SDM's UI is mid-migration: an **older AngularJS shell** renders the outer page and menu, while newer screens are a **modern Angular app served at `/Iapetus`** — both from the same backend.

## The idea
When you open SDM, the backend's thin MVC side serves the **legacy AngularJS shell** (`HomeController` / `IapetusController` rendering a Razor view). That shell draws the outer page — the logo, the header, and the **left navigation menu** — with an `<ng-view>` region for content.

Each menu link is one of two kinds:
- **Upgraded** — points at the **modern Angular SPA** under `/Iapetus/<feature>` (e.g. `/Iapetus/Schools`). Clicking it loads the new Angular 12 app, which is built with `--base-href Iapetus` and served by the same backend out of `wwwroot`.
- **Legacy** — stays in the old AngularJS shell (its content renders in `<ng-view>`).

So a single backend hosts **both** front ends: it serves the legacy shell, serves the Angular SPA's files at `/Iapetus`, and answers the `/api/*` calls both make. The migration is gradual — features move from the legacy shell to the Angular app one at a time, which is why the nav data marks each link "upgraded" or not.

## Why it matters
If you don't know there are two front ends, the codebase is confusing: you'll find both AngularJS (older) and Angular 12 (newer) code, and a menu that jumps between them. Knowing the split tells you *where* a given screen lives and why `/Iapetus` is in the URL.

## Watch out for
**"It's all one Angular app."** It isn't — there's the legacy AngularJS shell *and* the Angular 12 SPA at `/Iapetus`. A link's "upgraded" flag is what decides which one a click lands in.
