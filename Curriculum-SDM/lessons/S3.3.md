# S3.3 — Standalone Groups (rules, staff, DA-* linkage)

## In one line
A Standalone Group is a membership list SDM **owns outright** — you fill it either by **HR-attribute rules** or by **adding staff directly with start/end dates**, and you can link it to a **DA-\*** AAD group.

## The idea
Standalone Groups are the membership lists SDM **curates directly** (S1.4). Unlike composed or derived groups, whose membership rolls up from other groups, a standalone group's membership is maintained **by hand in SDM**. And unlike Schools (S3.1), which SDM only augments, SDM **owns** standalone groups outright — it can **create** and **delete** them.

There are two ways to put staff in a group:
- **Rule-based** — membership is driven by **HR attributes**. You define the rule and staff who match are in the group.
- **Staff-based** — you add a named staff member directly, with a **start date and end date**. This is what makes **temporary** membership possible: access that turns on and off on a schedule.

**View options** let you see the current **membership** of any group — who's in it and why.

A group can also be set up with **ultimate linkage to a DA-\* group**: the standalone group is associated with an Entra (AAD) `DA-*` security group. This is exactly how SDM **augments** the system-generated access (S1.3): the standalone group's membership is saved to DDH, and `Sync-DDH-AAD` — the sync that actually generates the `DA-*` access — picks it up and propagates it into the Azure group, where it then feeds the claims SDM reads.

This whole area is **being ported from an old JSON config file**. The role-based access that used to live in that file now lives in SDM as Standalone Groups — for example, the **Help Desk** supplies a staff member's **temporary access** by adding them to a group (with an end date) that's linked to the right `DA-*` group. SDM doesn't grant the access itself; it feeds `Sync-DDH-AAD`, which generates the membership in the Azure `DA-*` group, so the access takes effect at the user's next sign-in (S1.3).

Like every SDM edit, changes write to DDH with the usual `CreatedBy`/`UpdatedBy` audit trail.

## Why it matters
This is the practical lever behind "grant me access for two weeks." If you don't know that a standalone group's membership is **curated directly** (rule- or staff-based, with dates) and can be **linked to a DA-\* group**, you won't know where temporary access actually comes from — and you'll go hunting for a setting that doesn't exist. Knowing SDM **owns** these groups also tells you that, unlike a school, **creating and deleting** them here is legitimate.

## Watch out for
- **"Membership rolls up automatically like a composed group."** No — a standalone group's membership is **curated by hand**. It's filled by an HR-attribute rule or by directly added staff with start/end dates, not by composing other groups.
- **"SDM only augments these, like Schools."** The opposite — SDM **owns** standalone groups and can create and delete them. Schools (S3.1) come from a system of record; standalone groups do not.
- **"Adding someone to a DA-\*-linked group grants access instantly."** It doesn't — the membership is saved to DDH and reaches the user's token only at their **next sign-in** (S1.3).

## You've got this when you can…
- State the two ways to populate a standalone group: **rule-based** (HR attributes) and **staff-based** (a staff member with **start/end dates**), and use a view option to see its **membership**.
- Explain that a standalone group can be **linked to a DA-\* AAD group**, which is how it feeds authorization (S1.3) — e.g. Help-Desk **temporary** access.
- Say that this functionality is being **ported from the old JSON config**, and that SDM **owns** these groups (it can **create and delete** them), unlike augment-only Schools (S3.1).
