# S1.2 — How SDM is built (two repos, one app)

## In one line
SDM is **two repositories that deploy as one web app**: an Angular front-end and an ASP.NET Core back-end that serves it and exposes the API.

## The idea
- **Front-end** — `SupplementalDataManagerClient` (APP-0059): an **Angular 12 single-page app**. It's built with `--base-href Iapetus`, so it lives under `/Iapetus/` rather than the site root. Each screen calls the backend over `/api/*`.
- **Back-end** — `SupplementalDataManager` (APP-0058): an **ASP.NET Core 8** app that does two jobs at once — it **hosts the SPA** (the built front-end is copied into its `wwwroot/` at deploy time) and it **exposes ~30 REST controllers** under `/api/*`. Its domain logic and data access live in the `Cssd.IT.Portal.SupplementalDataManager` class library.
- **Database** — the backend reads and writes the **SchoolObjectModel** SQL database (part of DDH) through **EF Core**, using `SchoolObjectModelDbContext` for edits and a separate `ReportingContext` for read-only reporting views.

A single request, end to end:

```
Browser ──/Iapetus/* (SPA shell)  or  /api/* (JSON)──▶ ASP.NET Core 8 backend ──EF Core──▶ SchoolObjectModel DB
```

There's also a **legacy AngularJS shell** still in the mix: the backend's `IapetusController` / `HomeController` render the outer page, and older features run there while newer ones are the Angular SPA at `/Iapetus`. That's why a menu link is either an in-app `/Iapetus/...` route (the new app) or a legacy link.

## Why it matters
Knowing it's *one app from two repos* explains the deploy dance: you build the Angular app, copy its `dist/` into the backend's `wwwroot/`, and ship the backend. It also explains why both repos agree on the name **`Iapetus`** — the SPA's base-href and the backend's route must match.

## Watch out for
**"The front-end and back-end are separately hosted."** At runtime they're the *same* IIS app: the backend serves the SPA's files and the API from one origin. `Iapetus` is just the path the SPA is mounted under.
