# S2.3 — Editing the record: audit and soft-delete

## In one line
Every SDM edit is **attributable and reversible**: entities carry a GUID id, who-changed-it audit fields, and a soft-delete flag, and a change writes an `AuditLog` row — all in DDH.

## The idea
SDM holds **no data of its own** — it reads and writes the **DistrictDataHub (DDH)** database. The domain entities there follow a consistent shape:

- **`Id` is a GUID** — the stable key for each record.
- **`CreatedBy` / `UpdatedBy`** — audit fields stamped with the editing user, so every record remembers **who** last touched it (and when).
- **Soft delete** — records are marked deleted with a flag rather than physically removed, so a "delete" is **reversible** and history is preserved.
- **`AuditLog`** — a separate log captures a row per change, giving a who/what/when trail beyond the latest `UpdatedBy`.

Put together: an edit in SDM is never a silent overwrite. It's a tracked change against a stable record, attributed to a person, and recoverable. Because the data lives in DDH, that audit trail travels with the data — and the downstream `Sync-*` fleet picks up the change from there.

## Why it matters
This is what makes SDM safe as the *editorial* layer (S1.1). Authorized humans change authoritative data, so the system has to answer "who changed this, when, and can we undo it?" — and it does, via audit fields + soft delete + the `AuditLog`. When investigating a data issue, that trail is where you look.

## Watch out for
- **"Deleting removes the row."** It's a **soft** delete — a flag, not a physical removal — so it can be undone and the record's history survives.
- **"SDM stores the data."** No — DDH does. SDM is the editor; the rows (and their audit) live in the DDH database.
