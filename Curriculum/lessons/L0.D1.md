# L0.D1 — Dependency injection & constructor injection

## Generic skill (curated — don't re-teach)
**Inversion of control:** instead of a class creating the things it needs, it *declares* them as constructor parameters and is *handed* them by something else. So a class that needs an `IClock` writes `public Thing(IClock clock)` and receives one — it never calls `new SystemClock()`. The benefit: the class doesn't know or care which concrete implementation it gets, which makes it swappable and testable. If you can read a constructor parameter as "this class is handed a dependency," you're solid.
→ Refresher: **Microsoft Learn — dependency injection** (`learn.microsoft.com/dotnet/core/extensions/dependency-injection`).

## The Synnduit slice
Synnduit connectors get their dependencies the same way — through the constructor:

```csharp
public class TeamSiteWebPartSink : ISink<TeamSiteWebPart>
{
    private readonly ITeamSiteWebPartService service;

    public TeamSiteWebPartSink(ITeamSiteWebPartService service)   // handed in, not new-ed
    {
        this.service = service;
    }
    // ...uses this.service to talk to the destination...
}
```

The sink declares `ITeamSiteWebPartService` as a constructor parameter and stores it. It never writes `new TeamSiteWebPartService(...)`. Something else creates the service and supplies it. (In Synnduit that "something else" is **MEF** — the next concept, L0.D2 — but the *constructor-injection* idea is exactly the standard DI you already know.)

## Placement check
A constructor parameter `ITeamSiteWebPartService service` means the class **creates** the service, or **is handed** one? (Handed one.) Pass and you skip ahead.

## If this is shaky
Read the MS Learn DI page, then look at a sink constructor receiving its service — the parameter is a dependency provided from outside, not something the sink constructs.
