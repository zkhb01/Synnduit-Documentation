# L2.7 — Customizing the engine with pluggable operations

## In one line
Feeds and sinks aren't the only things you can plug in — the engine discovers **operation classes** (preprocessors, duplication rules, and more) the same way: **implement an interface, annotate the class, and MEF wires it up**.

## The idea
You've written a feed (`IFeed<T>`) and a sink (`ISink<T>`) and wired them with MEF (L2.5). The engine exposes several more extension points that follow the **exact same pattern** — implement the interface, tag the class with the matching attribute, take dependencies via `[ImportingConstructor]`, and MEF discovers it at runtime. The two you'll reach for most:

### Preprocessor — transform or reject an entity before it syncs
A `[PreprocessorOperation]` runs on each entity as it flows through, and can **change it** or **`Reject()`** it. From `Sync-DDH-SPO`:

```csharp
[PreprocessorOperation]
public class TeamSiteCalendarEventCategoryResolver : IPreprocessorOperation<TeamSiteCalendarEvent>
{
    [ImportingConstructor]
    public TeamSiteCalendarEventCategoryResolver(IContext context, IMapper mapper, IMessageLogger log) { ... }

    public void Preprocess(IPreprocessorEntity<TeamSiteCalendarEvent> e)
    {
        if (e.Origin == EntityOrigin.SourceSystem)
        {
            // resolve source category GUIDs to destination category IDs, then set the field…
            e.Entity.CategoryIds = this.GetCategoryIds(e).AsString();
            // …and if a value can't be resolved:
            //   log an error and e.Reject();
        }
    }
}
```

A **`Reject()`** produces the **`Rejected`** outcome (L1.10) — the record is deferred, not failed. Use a preprocessor to normalize/derive values or to gate records that aren't ready (e.g. a dependency isn't in the destination yet).

### Duplication rule — custom duplicate matching
A `[DuplicationRule]` replaces the default `[DuplicationKey]` matching (L1.11) with **your own logic** — useful when "is this already in the destination?" needs an API call or a rule a stored key can't express. Your `GetDuplicates` returns `Duplicate`s, each with a `MatchWeight`:

```csharp
[DuplicationRule]
public class TeamSiteDuplicationRule : IDuplicationRule<TeamSite>
{
    [ImportingConstructor]
    public TeamSiteDuplicationRule(ITeamSiteService teamSiteService) { ... }

    public IEnumerable<Duplicate> GetDuplicates(TeamSite entity)
    {
        var duplicates = new List<Duplicate>();
        if (this.teamSiteService.GetSite(entity.Url) != null)              // ask SharePoint directly
            duplicates.Add(new Duplicate(entity.Url, MatchWeight.Positive));
        return duplicates;
    }
}
```

`MatchWeight.Positive` means a confident match (link & merge); a weaker weight routes to **manual deduplication** — the same outcomes you learned in L1.11, now driven by your rule instead of a key.

### The rest of the family
Same interface + attribute + MEF pattern, less commonly needed:
- **`[Homogenizer]`** — normalize a value before the engine compares it (so trivial format differences don't read as changes).
- **`[EventReceiver]`** — receive engine events for custom logging or side-effects.

## Why it matters
Most integrations only need feeds, sinks, and POCOs. But when the destination's notion of "duplicate" is a live lookup, or a source value needs deriving/validating before it lands, these hooks are how you extend the engine **without modifying it** — the plug-in model (L1.3) all the way down.

## Watch out for
- **Forgetting the attribute.** Like a feed or sink, the class must carry its attribute (`[PreprocessorOperation]`, `[DuplicationRule]`, …) or MEF won't discover it — no error, it just never runs.
- **Confusing `Reject()` with an exception.** `Reject()` is a clean deferral (`Rejected` outcome, L1.10), not a failure.
- **Reaching for a `[DuplicationRule]` when a `[DuplicationKey]` would do.** Use the custom rule only when a stored key can't express the match (e.g. it needs an API call).
