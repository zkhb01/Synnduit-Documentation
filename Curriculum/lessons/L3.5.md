# L3.5 — Resolve a sync exception

## In one line
Most production exceptions are **known, repeatable cases** — read the message literally, match it to a root cause, apply the small fix. The `ExceptionHistoryWithResolutions/` folder is the catalogue.

## The idea
A handful of exceptions account for most real incidents. Three worth knowing:

**"Unable to resolve reference identifier" (Property: StaffId; Source System ID: '0017738')**
A child entity references a parent by an ID the engine can't find a mapping for. In the real case, a `Section` referenced `StaffId`, but **Staff hadn't registered PowerSchool as one of its source systems** — so the PowerSchool staff id had no mapping.
**Fix:** add the missing source system to the entity's `[SharedSourceSystemIdentifiers]` list (a POCO/wiring change, L2.1).

**`SqlException: Violation of UNIQUE KEY constraint … Cannot insert duplicate key`**
The engine tried to **Create** a record that already exists in the destination, because **StarBridge had no mapping** linking the source record to the existing destination row — so it didn't know to Update instead.
**Fix:** establish the missing mapping (or let dedup match it via `[DuplicationKey]`, L1.11) so the next run Updates rather than Inserts.

**`System.InvalidOperationException: No sink exists for the X entity type`** (and its siblings — "feed could not be found", "multiple feeds exist")
A connector isn't discoverable: the `[Sink]`/`[Feed]` is missing, mis-typed, or duplicated, so MEF (L2.5) can't bind exactly one.
**Fix:** check the connector's attribute wiring — exactly one `[Sink]`/`[Feed]` for that entity, correctly attributed.

**The process, every time:**
1. Get the exact message text (console, or `EntityException`/`Message` via L3.2/L3.3).
2. **Search `ExceptionHistoryWithResolutions/`** for that error — it's very likely already solved there.
3. Trace to the root cause and apply the documented fix; if it's new, add it to the folder.

## Why it matters
Treating each exception as a fresh mystery is slow. Most map to a one-line cause (a missing source-system registration, a missing mapping, a wiring typo). The catalogue turns "what is this?" into "oh, *that* one."

## Watch out for
- **Reading the message loosely.** It's literal: "No sink exists for X" means *that entity's* sink isn't discoverable — a wiring problem, not a data problem.
- **Fixing the symptom, not the cause** — e.g. manually inserting the duplicate instead of creating the mapping that prevents it recurring.

## You've got this when you can…
- Map each of the three common exceptions to its root cause and fix.
- Describe the read-message → search-history → fix-root-cause loop.
