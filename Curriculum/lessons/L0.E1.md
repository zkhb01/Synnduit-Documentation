# L0.E1 — Querying a source with Entity Framework

## Generic skill (curated — don't re-teach)
A `DbContext` is your handle to a database. You query it with LINQ — `.Where(...)` to filter, `.Select(...)` to project — and EF translates that to SQL. The catch most people know: **deferred execution.** Writing `context.Staff.Where(...)` builds a query but doesn't hit the database; it runs when you *enumerate* it (`.ToList()`, `foreach`, `.First()`). If you can say when a LINQ query actually executes, you're solid.
→ Refresher: **Microsoft Learn — EF querying** (`learn.microsoft.com/ef/core/querying`).

## The Synnduit slice
A feed is, mostly, an EF query that **projects rows into POCOs**. From `StaffFeed`:

```csharp
public IEntityCollection<Staff> LoadEntities()
{
    using var context = this.hradFactory.CreateHRAD();      // open a DbContext
    return context.CCS_HR_AD_SYNC
        .Where(Util.ActiveStaffWithManager)                 // filter (deferred)
        .Select(s => new Staff { EmployeeId = s.EMPLID, ... })  // project into the POCO
        .ToList();                                          // materialize → query runs here
}
```

Three beats: **open** a context, **query/project** into your entity type, **materialize** (`.ToList()`) to return the snapshot (L1.4/L1.8). The `.ToList()` matters — it's where the SQL actually executes and where the connection is still open.

## Placement check
When does `context.Staff.Where(...)` actually hit the database? (On enumeration — e.g. `.ToList()` — not when the line is written.) Pass and you skip ahead.

## If this is shaky
Read the MS Learn EF querying page, then trace `StaffFeed`'s `.Where().Select().ToList()`. Watch the gotcha: **materialize (`.ToList()`) before doing complex C# work**, so you're not running unsupported logic inside the EF-translated query or after the context is disposed.
