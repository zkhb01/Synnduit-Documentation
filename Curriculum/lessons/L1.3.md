# L1.3 — The engine model (you plug things in)

## In one line
Synnduit is an **engine you don't modify** — you supply two connectors (source and destination), and the engine does the diffing in between.

## The idea
Think of Synnduit as a fixed engine with two plug-in slots:

```
    ┌──────────┐   snapshot    ┌────────────┐   delta    ┌──────────────┐
    │  SOURCE  │ ────────────▶ │  Synnduit  │ ─────────▶ │ DESTINATION  │
    │ (HR, PS) │               │   engine   │            │    (DDH)     │
    └──────────┘               └─────┬──────┘            └──────────────┘
                                     │
                                     ▼
                            ┌─────────────────┐
                            │   StarBridge    │  ← mappings, change history,
                            │ (SQL bookkeeping)│   transactions, exceptions
                            └─────────────────┘
```

Your job is the two boxes on the outside:

1. **A source connector** — code that reads a *data snapshot* from a system (Oracle, AD, an API, a JSON file). In Synnduit this is a **feed**.
2. **A destination connector** — code that knows how to create / update / delete records in the target. In Synnduit this is a **sink**.

**Synnduit does the hard part in the middle:** it compares your new snapshot to what it saw last time, figures out what changed (the **delta**), and applies only those changes to the destination — recording mappings, change history, and outcomes in StarBridge as it goes.

You never edit the engine. You write connectors against its interfaces and Synnduit loads them. As the overview deck puts it: *"Synnduit is an engine! You implement connections to your external systems… you provide data snapshots, Synnduit detects and processes the delta."*

## Why it matters
This is the division of labor that makes the whole platform tractable. The mechanically hard, easy-to-get-wrong parts — diffing, deduplication, change logging, error thresholds, garbage collection — live *inside* the engine and are written once. You only write the system-specific glue. CCSD reports roughly a **75% reduction in custom code** because of this split.

## Watch out for
**"To add a new integration I modify Synnduit."** You don't. Adding an integration means writing a new feed and a new sink (and the entity classes) in *your* library; the engine binary stays untouched. If you find yourself wanting to change engine behavior, the intended path is the override/extension points, not editing the engine.

## You've got this when you can…
- State that you implement a **source connector (feed)** and a **destination connector (sink)**, and the engine computes & applies the delta.
- Explain that the engine is fixed; the connectors are yours.
- Place the three pieces in order: **SOURCE → (engine) → DESTINATION**.
