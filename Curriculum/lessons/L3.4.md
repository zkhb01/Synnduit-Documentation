# L3.4 — When a threshold aborts a run

## In one line
A run that **stops itself** usually isn't a bug — it's an **abort threshold** doing its job, protecting the destination from a bad source feed.

## The idea
Synnduit's safety thresholds (L1.12) live in `appsettings.json` and halt a run when something looks dangerous:

```jsonc
"ExceptionHandling": {
  "SegmentAbortThreshold": 30,                       // abort the segment after 30 exceptions
  "RunAbortThreshold": 101,                           // abort the whole run after 101
  "OrphanMappingPercentageAbortThreshold": 0.05,      // preemptive: abort during migration if >5% of mappings orphan
  "GarbageCollectionPercentageAbortThreshold": 0.05   // abort during GC if >5% of the destination would be deleted
}
```

The two percentage thresholds are the important ones operationally, and they fire at **different points in the run**:

- **Orphan-mapping** — checked *preemptively, during the Migration segment, before any garbage collection runs.* As the migration identifies mappings whose source record is gone (so the destination record is slated for deactivation/removal), it aborts once the identified percentage crosses the limit — you'll see it in a `Migration` segment (`"Removing N orphan mappings ... the threshold of X% ... has been reached, and the run has been aborted"`).
- **Garbage-collection / deletion** — checked *during the GarbageCollection segments themselves*, when a segment would delete more than the configured percentage of the destination.

Both share the same root cause: a **broken source feed** — the source query returned far fewer rows than reality (an outage, a bad filter, a credential problem), so the engine thinks thousands of records "disappeared" and is about to deactivate/delete them. Either threshold stops that; the orphan-mapping one just catches it earlier.

**Config tip: set the two percentages to the same value** (both `0.05` above). They guard the same failure, so a single consistent "how much removal is too much" line is what you want. Because the orphan-mapping check is **preemptive**, it usually trips first — aborting cleanly during migration, before the GC segments run and before anything is deleted — which is why it's the more beneficial of the two to rely on. The matching GC value is the backstop that covers anything the orphan check doesn't (e.g. an entity configured with `None` orphan behavior).

**Tune the percentage to the migrator, not just globally.** Production usually runs a tight **5%**, but the threshold can be **overridden per segment/migrator** (a per-segment value takes precedence over the application-wide default). Size the limit to what a *legitimate* run could plausibly remove: 5% is a strong guard on a large entity (5% of 850,000 is a lot of records to lose), but on a small feed one dropped record is already a big share (1 of 10 = 10%), so a strict 5% would false-trip on normal variation — a low-volume migrator may warrant a higher limit. So when a *small* feed keeps aborting on a legitimate change, raising the threshold **for that migrator** is the right move (step 2 above) — not lowering the global value or removing the guard that protects the large entities.

**How to respond, in order:**
1. **Look at the source first.** Did the feed return a plausible row count? (The console's "Loading source system entities … N loaded" is the tell.) A suspiciously low N = a broken feed; fix the source, don't touch the threshold.
2. **Only if the large change is genuinely expected** (a real bulk delete, a school closing) raise the threshold for that run intentionally.

## Recovering after an orphan-mapping abort
Once you've fixed the feed, **just re-run — you do not need to restore the StarBridge database.** The orphan-mapping abort is *preemptive*: it fires **before** any orphan mapping is deactivated or removed, so the mappings and every destination record are exactly as they were. (In the engine, the threshold check throws *before* the loop that changes any mapping state — which is why the console shows `Removing N orphan mappings: .00%`, aborting at 0.00%.)

On the fixed re-run, the records that had "disappeared" are back in the snapshot and **match their existing mappings**, so they come through as **`NoChangesDetected`** (or `ChangesDetectedAndMerged` if a value genuinely changed while the feed was down). They are **not** treated as new inserts, and they do **not** hit duplicate detection — dedup only runs for *unmapped* records (L1.11), and these were never unmapped.

- **Don't restore from backup.** There's nothing to undo, and a restore would discard legitimate work and mappings created before the abort.
- The `DuplicateDetectedNoChangesMerged` path — recovered records re-matched by `[DuplicationKey]` — only happens if the orphan mappings were actually **removed** (the threshold disabled or raised so the run *completed* the removal). Even then there are no duplicate rows, just extra transaction churn; the threshold is what spares you that.
- **Caveat:** with the run-abort setting on, the whole run stops at the first tripped segment. Segments that finished *earlier* in the same run may have processed their own orphans (if each was under threshold); those specific records would recover via the dedup path on re-run instead. A glitch isolated to one feed re-runs cleanly as `NoChangesDetected`.

## Why it matters
An abort feels like a failure, but it's the guardrail working — it's the difference between "the sync stopped" and "the sync wiped the DDH." Reflexively raising the threshold to make the run "pass" can turn a caught problem into a data-loss incident.

## Watch out for
- **Bumping the threshold to force the run through** without checking the source — that defeats the protection.
- **Confusing an exception-count abort with a percentage abort** — the first is "too many errors," the second is "too much deletion/orphaning."
