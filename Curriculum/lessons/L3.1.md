# L3.1 — Run a sync and read the console

## In one line
A scheduled run (via Windows Task Scheduler) has no *live* console — **re-run the Run's `.cmd` from a command prompt** to watch it live (but ensure it's not still running), and read the **per-segment outcome counts** to see what happened. Every run also writes a persistent record to a **Serilog log file**.

## The idea
Runs are scheduled via Windows Task Scheduler, so there's no console to watch. To see live progress, launch the same command yourself — `Synnduit <RunName> <UserSecretGuid>` (the shape from L2.6 / README §5.3, usually wrapped in a `.cmd`).

Each **segment** prints a header and a tally of the **transaction outcomes** from L1.10:

```
Segment 1 out of 2:
Type: Migration   Source system: Power School   Entity type: Section
Loading entity identifier mappings ... 1,097,311 mappings loaded.
Loading source system entities ... 53,243 entities loaded.

Skipped:
No changes detected:        52,108
Changes detected & merged:     431
New entity created:            704
Rejected:                        8
Exception thrown:                0
```

Reading that tally tells you the run's story at a glance: mostly **No changes detected** is a healthy no-op; a wave of **New entity created** is an initial load; any **Exception thrown** needs follow-up (L3.2/L3.5); **Rejected** means an entity couldn't be processed *yet* (often a dependency missing this pass — not an error by itself).

## It's also written to a log file (Serilog)
The console view is live and updates *in place*, but it isn't the only record. A **`FileLogger`** — an `[EventReceiver]` (the extension point from L2.7) running alongside the console logger — emits a clean, **one-line-per-event** log through **Serilog** to the **file sink configured in the running Synnduit's `appsettings.json`** (`Serilog` → `WriteTo` → `File` → `path`, rolling daily). It captures each segment's **final outcome tally** plus the notable events — exceptions, manual-dedup referrals, and threshold aborts (with the actual percentage vs. the threshold).

Because it runs on *every* execution, **even a scheduled run you never watched leaves a greppable log** — so when you can't re-run live, read the log file instead. It records the *final* state, not the live in-place updates.

## Why it matters
The console is the fastest triage there is. Before opening StarBridge or the dashboard, a manual re-run tells you whether a run is clean, doing a big load, or throwing — and which segment/entity is involved.

## Watch out for
- **Expecting a *live* console from the scheduled run** — there isn't one; re-run manually to watch, *or* read the Serilog log file for the record the run left.
- **Jumbled / misaligned console output on Windows** — the console logger updates the tally *in place*, which the new **Windows Terminal** can render misaligned. Switch the default terminal to **Windows Console Host** (Windows Settings → System → *For developers* → *Terminal*; or Windows Terminal → Startup → *Default terminal application*) to restore the intended display. The log file is unaffected — it's plain one-line-per-event.
- **Reading "Rejected" as an error** — it isn't; it's "try again later." With correct parent-before-child ordering rejects should be *rare* — but a long running segment against a volatile data source can still produce them (e.g. a Student created just after the Student segment finished, so the StudentContact segment can't map it yet). They clear on the next run.
- **Ignoring a non-zero "Exception thrown"** — that's the one that always needs a look.

## You've got this when you can…
- Re-run a Run's `.cmd` manually and find the per-segment outcome tally.
- Say what a run did from its counts (clean no-op vs. initial load vs. errors to chase).
- Find the run's persistent record in the **Serilog log file** (path from `appsettings.json`), and switch to **Windows Console Host** if the live console looks misaligned.
