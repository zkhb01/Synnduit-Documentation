# L1.7 — Run & Segment

## In one line
A **Run** is a scheduled job that syncs a set of entities; a **Segment** is one ordered step inside it — either a `Migration` (push changes in) or a `GarbageCollection` (clean up records the source dropped).

## The idea
A **Run** (also called a Migrator) is the unit you schedule — at CCSD via Windows Task Scheduler, launched as `Synnduit <RunName> <RunGuid>`. The GUID ties the run to its history in StarBridge so identity stays consistent across executions.

A Run is a named, **ordered list of Segments**. Each Segment is one step on one entity type, of one of two types:

- **`Migration`** — push the delta from source into the destination (create/update).
- **`GarbageCollection`** — handle destination records whose source has **disappeared** (e.g. delete or unmap them).

**Order matters, because of foreign keys.** From `appsettings.json`:

```jsonc
"Segments": [
  { "Type": "Migration",         "EntityType": "School" },
  { "Type": "Migration",         "EntityType": "Student" },         // student references a school
  { "Type": "Migration",         "EntityType": "StudentAddress" },  // address references a student
  { "Type": "GarbageCollection", "EntityType": "StudentAddress" },
  { "Type": "GarbageCollection", "EntityType": "Student" },
  { "Type": "GarbageCollection", "EntityType": "School" }
]
```

Migrate **parents before children** (a Student can't reference a School that isn't there yet). Garbage-collect in **reverse** — children before parents — so you don't delete a School while Students still point at it. It's the same dependency logic you'd use inserting into and deleting from foreign-keyed tables.

## Why it matters
The Segment list *is* the sync's recipe — reading it tells you exactly what an integration does and in what order. And getting the order wrong produces foreign-key violations, which is a real, common failure mode (several entries in `ExceptionHistoryWithResolutions/` are reference/foreign-key errors).

## Watch out for
**"Migration and GarbageCollection are the same direction, so order doesn't matter."** They're opposites. Migration adds/updates and needs parents first; GarbageCollection removes and needs children first. Listing GC in the same order as Migration (parents first) can break referential integrity.

## You've got this when you can…
- Define a Run (scheduled sync of a set of entities) and a Segment (one step: Migration or GarbageCollection).
- Say which Segment type removes destination records whose source disappeared (GarbageCollection).
- Explain why you migrate School before Student but garbage-collect Student before School.
