# L0.D2 — MEF composition in Synnduit

> **Read this even if you know dependency injection cold.** Synnduit does *not* use the
> `Microsoft.Extensions.DependencyInjection` container most .NET devs know. It uses **MEF**
> (the Managed Extensibility Framework), which composes by **attribute-driven discovery**,
> not by registering services in a container at startup. This is exactly where strong DI
> devs get surprised — there's no `services.AddScoped<...>()` anywhere to grep for.

## The DI you know vs. the MEF Synnduit uses

| | Typical .NET DI (`Microsoft.Extensions.DI`) | MEF (Synnduit) |
|---|---|---|
| How a type is registered | You call `services.AddSingleton<IFoo, Foo>()` in startup | You **decorate** the type with an attribute; MEF **discovers** it |
| Where the wiring lives | A central composition root / `Program.cs` | Spread across the parts themselves, as attributes |
| How you find "what's registered" | Read the startup registration code | Look for `[Export]` / `[Sink]` / `[Feed]` attributes on classes |
| How a class receives deps | Constructor injection (the container resolves) | Constructor injection too — but the ctor is marked `[ImportingConstructor]` |

The *constructor-injection* idea from L0.D1 still holds. What changes is **discovery**: MEF scans assemblies for attributed **parts** and composes them, so there is no explicit registration list.

## The Synnduit slice — the attributes that do the wiring

- **`[Sink(DestinationSystem = typeof(...))]` / `[Feed(SourceSystem = typeof(...))]`** — mark a class as a discoverable connector **part**. This is how the engine finds your sink/feed without you registering it anywhere.
- **`[Export(typeof(IService))]`** — publishes a class as the implementation of a service contract, so other parts can import it. Pair it with **`[PartCreationPolicy(CreationPolicy.Shared)]`** to make it a single shared instance (MEF's equivalent of a singleton).
- **`[ImportingConstructor]`** — marks the constructor MEF should use to inject the imported services. This is the MEF counterpart to "the constructor the container resolves."

Putting it together (illustrative shape — see `TeamSiteWebPartService.cs` and the Sync-DDH-SPO sinks for the real code):

```csharp
[Export(typeof(ITeamSiteWebPartService))]              // publish this as the service
[PartCreationPolicy(CreationPolicy.Shared)]            // one shared instance
public class TeamSiteWebPartService : ITeamSiteWebPartService { ... }

[Sink(DestinationSystem = typeof(SharePointOnline))]   // discoverable connector part
public class TeamSiteWebPartSink : ISink<TeamSiteWebPart>
{
    [ImportingConstructor]                             // MEF injects here
    public TeamSiteWebPartSink(ITeamSiteWebPartService service) { ... }
}
```

So: the service `[Export]`s itself, the sink is discovered via `[Sink]`, and MEF hands the exported service into the sink's `[ImportingConstructor]`. No registration code — the attributes *are* the registration.

## Placement check
Two things: (1) What does `[ImportingConstructor]` tell MEF? (Use this constructor for injection.) (2) How does the sink get its `ITeamSiteWebPartService` — registered in startup, or discovered via `[Export]` and injected by MEF? (Discovered + injected.)

## If this is shaky
Don't reach for `Microsoft.Extensions.DI` intuition. Map it across: `AddSingleton` → `[Export]` + `[PartCreationPolicy(Shared)]`; "the resolved constructor" → `[ImportingConstructor]`; "find the registrations" → "find the `[Export]`/`[Sink]`/`[Feed]` attributes." Then read one real `[Export]`/`[ImportingConstructor]` pair in `TeamSiteWebPartService.cs` + its sink.
