# L3.7 — Splitting into multiple StarBridge databases

## In one line
The ideal is **one StarBridge database and one program** managing every entity — you split into **multiple StarBridge databases** only when a concrete driver (running concurrently, or keeping some data fresher) makes the single-database setup impractical.

## The idea
Recall from L1.5: a **StarBridge database** is Synnduit's bookkeeping store, and **only one process may run against it at a time.** Two concurrent processes would corrupt the shared mappings, transaction log, and resumability state (L1.12).

In principle you'd run **one StarBridge database with one program**, managing all entities across every source and destination. That's the simplest thing to deploy, schedule, and monitor. In practice a single database often grows to span **multiple sources feeding one destination, plus multiple destinations** — and that's fine; many source → destination flows can live comfortably in one database (as `Sync-SRC-DDH` does across its entities).

You reach for a **split** — carving the entities into two or more StarBridge databases, each with its own program/Run — when the single-database setup starts to hurt:

- **Concurrency.** One process per database means everything in that database syncs **serially**, inside one run window. If two groups of entities need to run **at the same time** — to hit an SLA, or simply to finish overnight — they must live in **separate databases**. Separate databases can run in parallel because each has its own process and its own bookkeeping.
- **Data freshness.** Sources refresh at different cadences — one is near-real-time, another is nightly. In one database they're coupled to a single schedule. Split them, and the fast-moving source can run every few minutes on its own program while the slow one runs nightly, each independent of the other.
- **Isolation & evolution** (secondary). A separate database limits blast radius — a stuck or aborted run in one doesn't hold up the others — and lets a group of entities be deployed, scheduled, and evolved on its own.

The cost of splitting is more moving parts: more databases, more programs/scheduled jobs, and more dashboards to watch. So it's a **deliberate tradeoff**, not a default — split when a driver above justifies the added operational surface.

CSSD runs **8 StarBridge databases** in production for exactly these reasons — grouping entities that belong together and can share one serial run window, and separating the groups that need to run concurrently or on different schedules.

## Why it matters
Getting this wrong at either extreme costs you. Cram everything into one database and you can't run concurrently or keep fast-moving data fresh. Split reflexively and you drown in databases and schedules to maintain. Knowing the drivers lets you make the call for a reason, not by reflex.

## Watch out for
- **Running two processes against one StarBridge database to "go faster."** This is the one thing you must never do — it corrupts the bookkeeping. Concurrency comes from *separate* databases, not parallel processes on one.
- **Assuming multiple sources or multiple destinations force a split.** They don't — one database happily manages many source → destination flows. Split for concurrency, freshness, or isolation — not just because there's more than one system involved.
- **Splitting without accounting for the operational cost** — every new database is another program to schedule, run, and monitor.
