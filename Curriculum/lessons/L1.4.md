# L1.4 — Delta detection (snapshot → delta)

## In one line
Your feed always hands Synnduit a **full snapshot**; the engine compares it to last run and processes **only what changed** (the delta).

## The idea
Here is the part that surprises people: **your source connector returns *everything*, every run.** `StaffFeed.LoadEntities()` returns all 5,000 staff each time — not "the ones that changed." You don't track changes yourself.

Synnduit does the change detection for you:

1. Your feed emits a complete **snapshot** of the source's current state.
2. The engine compares that snapshot against the **recorded state from the last run** (kept in StarBridge).
3. It computes the **delta** — new records, changed records, and records that disappeared — and applies *only* those to the destination.

So even though the feed returns 5,000 staff, if only 3 changed since yesterday, the destination gets 3 updates — not 5,000.

**Snapshot in, delta out.**

## Why it matters
It changes how you write a feed: you write the *simple* thing (query everything, return it) and let the engine do the *hard* thing (figure out what's different). You never write "what changed since last time" logic — and you never have to, which is a major reason integrations get smaller and less buggy.

## Watch out for
**"If the feed returns all 5,000 records, the destination gets 5,000 writes."** No — returning a full snapshot is not the same as applying a full reload. The engine diffs the snapshot against last run's recorded state and touches only the differences. A record that's identical to last run produces *no* destination write (it gets the `NoChangesDetected` outcome).

## You've got this when you can…
- Explain that the feed emits a **full snapshot** every run, not just changes.
- Explain that the engine diffs the snapshot against last run and applies only the **delta**.
- Answer "the feed returned all 5,000 rows — does the destination get 5,000 updates?" with *no, only the changed ones.*
