# L1.12 — Thresholds & resumability

## In one line
Two safety features: **abort thresholds** stop a run before a bad feed can wreck the destination, and **resumability** means a crash mid-run loses no data — the next run picks up where it left off.

## The idea
Delta detection trusts your snapshot. So what happens when the snapshot is *wrong*? Picture a feed that should return 65,000 students but, due to a bug, returns **0**. Without protection, the engine would conclude every student disappeared and garbage-collect the entire destination entity. Thresholds are the guardrails against exactly this.

**Abort thresholds** (configured in `appsettings.json` under `ExceptionHandling`):

```jsonc
"ExceptionHandling": {
  "SegmentAbortThreshold": 30,                       // abort a segment after 30 exceptions
  "RunAbortThreshold": 101,                           // abort the whole run after this many
  "OrphanMappingPercentageAbortThreshold": 0.05,     // preemptive: abort during migration if >5% of mappings orphan
  "GarbageCollectionPercentageAbortThreshold": 0.05  // abort during GC if >5% of the destination would be deleted
}
```

- **Exception thresholds** — abort a segment (or the whole run) once too many records throw exceptions.
- **Deletion / garbage-collection threshold** — during the **GarbageCollection** segments, if a segment would delete more than the configured percentage of the destination, **abort instead**. In the 0-students example, comparing 0 against 65,000 blows past the 5% line and the run stops. Setting the percentage to 100% allows full deletion; omitting it assumes 100%.
- **Orphan-mapping threshold** — a **preemptive** version of the same guard, checked *during the Migration segment, before any garbage collection runs*. As it migrates, the engine identifies **orphan mappings** — mappings whose source record is no longer in the snapshot, so the destination record is slated for deactivation/removal. If the percentage of mappings identified for removal exceeds the threshold, the run aborts *before* GC deletes anything.

Here a Staff migration has 12,181 destination records cached but the feed loads only 17 — a broken feed — so nearly every mapping looks orphaned. The orphan-mapping threshold catches it inside the Migration segment, before any GarbageCollection runs:

```text
Segment 31 out of 209:
  Type: Migration
  Entity type: Staff

Caching destination system entities ... 12,181 entities cached.
Loading source system entities ... 17 entities loaded.
No changes detected: 17 ( 2,554 )
New entity created: 0 ( 9 )

Migration progress: 100.00%
Removing 116 orphan mappings: .00%

The threshold of 60.00% orphan mappings identified for deactivation/removal has been reached
(actual percentage identified: 87.22%), and the run has been aborted.
```

The 87.22% of mappings flagged for removal blew past the configured 60% orphan-mapping limit, so the run aborted *before* the GarbageCollection segments — the destination was never touched. (That 60% was a **test** setting; production is typically much tighter — see below.)

**Lean on the orphan-mapping threshold, and keep the two percentages equal.** Of the two removal guards, the orphan-mapping threshold is the more valuable: because it fires during migration *before* any deletion, an abort leaves the mappings and destination untouched, so you fix the feed and simply re-run (L3.4). Set `OrphanMappingPercentageAbortThreshold` and `GarbageCollectionPercentageAbortThreshold` to the **same value** — they guard the same failure, so "how much removal is too much" should be one consistent line. With them equal, the preemptive orphan check typically trips first and spares you the GC pass entirely; the matching GC value is the backstop for anything the orphan check doesn't cover (e.g. an entity whose orphan behavior is `None` — configured via `OrphanMappingBehavior`; the deletion scope and orphan disposition are themselves tunable, see L2.8).

**Tune the percentage to the migrator's data volume.** Production usually runs a tight **5%**, but the right value depends on the entity's size, and it can be **set per migrator/segment** (a per-segment value overrides the application-wide default). 5% is a strong guard on a large entity — 5% of 850,000 records is a big loss worth stopping. But on a tiny feed one dropped record is already a large share (1 of 10 = 10%), so a strict 5% would abort on normal variation; a small-volume migrator may warrant a higher limit. Match the setting to what a *legitimate* run could plausibly remove.

**Resumability** is the other half: if the server crashes mid-run, no data is lost. Because StarBridge records progress as the run goes, the next execution resumes from where it stopped rather than redoing or corrupting work.

## Why it matters
These features are why an automated, unattended sync is *safe* to schedule. A bad upstream extract is not a hypothetical — it's the failure these settings exist for. Thresholds turn "a bad feed silently wiped the destination" into "the run aborted and alerted," and resumability turns "the box rebooted during the run" into a non-event.

## Watch out for
**Assuming the engine will always "just sync what it's told."** It won't, by design — if a run would breach a threshold it **aborts** rather than proceed. That's not a malfunction; it's the safety net doing its job. (And remember: an omitted deletion percentage defaults to 100%, i.e. *no* deletion guard — so the protection is only there if it's configured.)
