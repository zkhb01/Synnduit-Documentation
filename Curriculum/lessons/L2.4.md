# L2.4 — Sink + CacheFeed

## In one line
A **cache feed** (`ICacheFeed<X>`) lets the engine **re-read the destination's current state** so it can diff against it — and it's usually the **same class as the sink**.

## The idea
The feed (L2.2) gives the engine the *source* snapshot. To compute what actually changed on the *destination* side — and to garbage-collect — the engine also needs to read the destination's current records. That's `ICacheFeed<X>`.

Because the sink already knows how to talk to the destination, you typically implement both interfaces on **one class**:

```csharp
[Sink(DestinationSystem = typeof(SchoolObjectModel))]
public class TeamSiteWebPartSinkAndCacheFeed
    : ISink<TeamSiteWebPart>, ICacheFeed<TeamSiteWebPart>
{
    private readonly ITeamSiteWebPartService service;

    [ImportingConstructor]
    public TeamSiteWebPartSinkAndCacheFeed(ITeamSiteWebPartService service)
        => this.service = service;

    // ISink<T> members: New / Create / Get / Update / Delete  ...

    // ICacheFeed<T>: hand the engine the destination's current entities to diff against.
    public IEntityCollection<TeamSiteWebPart> LoadEntities()
        => this.service.GetAll().ToList();
}
```

One class can implement several interfaces (L0.O1) — here it's both the writer (sink) and the destination reader (cache feed). The README notes this combination explicitly (see `SinkAndCacheFeed.cs`).

## Why it matters
Without the cache feed the engine can't see the destination's current state, so it can't reliably diff or garbage-collect. Combining it with the sink avoids duplicating the destination-access code.

## Watch out for
- **Thinking the cache feed reads the *source*** — it reads the **destination** (the feed reads the source).
- **Materialize here too** — like any feed, `LoadEntities()` should return a materialized collection.
- **Assuming you need two classes** — one class implementing both `ISink<T>` and `ICacheFeed<T>` is the common, intended shape.
