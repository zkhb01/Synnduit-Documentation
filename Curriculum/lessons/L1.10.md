# L1.10 — Transaction outcomes

## In one line
Every record, in every run, ends with exactly one **transaction outcome** — and reading the counts of those outcomes is how you read what a run did.

## The idea
When the engine processes a source record, the result is recorded as one **outcome** in StarBridge's `EntityTransaction` table (and summarized as counts in the console). There are **11** of them (`EntityTransactionOutcome` in the engine source). The ones you'll see most:

| Outcome | What it means |
|---|---|
| `NewEntityCreated` (10) | No mapping existed and it wasn't a duplicate → a new destination record was created |
| `ChangesDetectedAndMerged` (5) | Mapping existed, fields changed → the changes were merged into the destination |
| `NoChangesDetected` (3) | Mapping existed, nothing changed since last run → no action |
| `NoChangesMerged` (4) | Changes were detected but the merge produced nothing to propagate to the destination |
| `Skipped` (1) | A mapping existed and settings said to skip already-mapped entities |
| `Rejected` (2) | A preprocessor deferred it (e.g. a dependency isn't in the destination yet) — **not an error**; retried later |
| `DuplicateDetectedChangesMerged` (7) | No mapping, but matched an existing record by dedup → mapping created + merged |
| `DuplicateDetectedNoChangesMerged` (8) | Same, but nothing needed merging |
| `ReferredForManualDeduplication` (9) | Possible duplicate(s) found → sent for a human to decide |
| `NotFoundInDestinationSystem` (6) | Mapping existed but the destination record was gone |
| `ExceptionThrown` (11) | An error occurred while processing the record |

Notice the outcomes are just the L1.4/L1.6 logic made visible: *mapping? → changed? → duplicate?* For example, "mapping exists + nothing changed" is exactly `NoChangesDetected`.

## Why it matters
Outcomes are the primary way you **read a run**. After a run, the console prints counts; a healthy daily run is mostly `NoChangesDetected` with a few `ChangesDetectedAndMerged`. A spike in `ExceptionThrown`, an unexpected pile of `NewEntityCreated` (did mappings vanish?), or lots of `Rejected` that never clear all tell a story. When triaging, you query `EntityTransaction` for the per-record outcome.

## Watch out for
**Reading `Rejected` as an error.** It isn't. `Rejected` means a preprocessor deferred the record — typically because something it depends on isn't in the destination yet — and it will be retried. The actual error outcome is `ExceptionThrown`. Confusing the two sends you chasing failures that aren't failures.

## You've got this when you can…
- State that every record gets exactly one outcome, stored in `EntityTransaction`, and that outcomes are how you read a run.
- Predict the outcome for a simple case (e.g. mapping exists + no change → `NoChangesDetected`).
- Explain why `Rejected` is *not* an error, and that `ExceptionThrown` is the error outcome.
