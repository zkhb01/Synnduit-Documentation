# L3.6 — Monitor with the Synnduit Dashboard

## In one line
The **Synnduit Dashboard** sits on top of any StarBridge DB and gives you a **visual history of runs and outcomes** — the at-a-glance view, with the SQL scripts behind it for deep triage.

## The idea
Everything you queried by hand in L3.2/L3.3 — runs, transaction outcomes, exceptions over time — the dashboard renders visually. It can be pointed at **any StarBridge database** (CSSD runs **8 in production**, one per Run/sync grouping).

It reads StarBridge's **`Console` views** (the same `Console.EntityTransaction` you queried in L3.2). For an older StarBridge DB that predates those views, the dashboard's setup creates them first:
- Copy the StarBridge DB to a local machine; in SSMS, check whether it has the `Console` views.
- If not, run the two setup scripts from `C:\Repos\SynnduitDashboard\` (see *Setting up the Starbridge Dashboard.docx*).

**Dashboard vs. scripts:** use the dashboard to *notice* something (a run with a spike of exceptions, an unusual delete count); drop to the `DiagnosticScripts/` (L3.3) to *pinpoint* the offending records and read the message text.

## Why it matters
Querying tables by hand is great for a known problem but poor for noticing problems. The dashboard is the monitoring layer — it surfaces the run that needs attention so you know *when* to open the scripts.

## Watch out for
- **Expecting it to work on a bare StarBridge DB** — it needs the `Console` views; run the setup scripts if they're missing.
- **Treating the dashboard as the whole toolkit** — it's for monitoring/visibility; root-cause triage still happens in the scripts and StarBridge tables.
