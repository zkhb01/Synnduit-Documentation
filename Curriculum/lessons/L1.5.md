# L1.5 — StarBridge (the bookkeeping database)

## In one line
**StarBridge** is the SQL database where Synnduit keeps its memory — mappings, transactions, value changes, and exceptions — Any given Run of Synnduit is performed against only **one StarBridge DB**. 
You can spin up multiple Starbridge databases depending of your syncing needs, what needs to be synced together. CSSD currently has 8 separate Starbridge databases.<br>
**Note** you should never have more than one process running at a time syncing the same Starbridge database.

## The idea
Synnduit's "version control" powers have to live somewhere. That somewhere is **StarBridge**, a SQL database the engine reads and writes as it runs. It is *not* the destination — it's a separate bookkeeping store that sits beside the engine.

What StarBridge remembers:

- **Mappings** — the link between each source record's ID and the destination record's ID.
- **Transactions** (`EntityTransaction`) — the per-record outcome of every record in every run.
- **Value changes** (`EntityValueChange`) — field-level diffs: what value changed, from what, to what, when.
- **Exceptions** (`EntityException`) — errors encountered while processing a record.

There is **one StarBridge database per Run**. At CSSD the `Sync-SRC-DDH` integration uses three — `StarBridge-Hrad`, `StarBridge-School`, `StarBridge-Stdnt` — each owning its own slice of entities and its own bookkeeping.

When something goes wrong, StarBridge is where you look: the diagnostic SQL scripts in `DiagnosticScripts/` query exactly these tables, and the Synnduit Dashboard visualizes them.

## Why it matters
StarBridge is *how* delta detection and mappings actually work — "last run's recorded state" (L1.4) and "the remembered link" (L1.6) are rows in StarBridge. It's also your primary troubleshooting surface: per-record outcomes, field-level history, and errors are all queryable there.

## Watch out for
**"The bookkeeping lives in the destination database."** It doesn't. The destination holds the synced *data*; StarBridge holds Synnduit's *records about* that data (mappings, history, outcomes, errors). They're separate databases with separate jobs.
