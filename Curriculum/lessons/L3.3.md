# L3.3 — Diagnose with the SQL scripts

## In one line
The repo's **`DiagnosticScripts/`** folder is a ready-made triage toolbox — **match the symptom to the script** instead of writing SQL from scratch.

## The idea
Each script targets a common question. The ones you'll reach for most:

| Symptom / question | Script |
|---|---|
| What outcomes did records get? | `Starbridge-Transactions.sql` |
| Show me the exception / rejection **text** | `Starbridge-ExceptionRejections.sql` |
| Got *"An item with the same key has already been added"* Exception? | `Starbridge-CorruptionCheck.sql` |
| Source + mapping exist, but the destination record is gone (Outcome 6) | `Starbridge-NotFoundInDestination.sql` |
| What field changed, from what to what? | `Starbridge-ValueChange.sql` |
| What did this run delete? | `Starbridge-Deletions.sql` |
| What's actually stored for this entity? | `Starbridge-SerializedEntityData.sql` |

The message text isn't in `EntityTransaction` — it's joined out of `Operation` → `Message`, which is what `ExceptionRejections` does. Messages carry a **Type**: `1 = Rejection`, `2 = Warning`, `3 = Exception`, `4 = Information`:

```sql
SELECT o.[TimeStamp], m.[Type], m.[Text], et.[Name] AS EntityType
FROM [dbo].[Operation] o
  INNER JOIN [dbo].[OperationMessage] om ON o.[Id] = om.[OperationId]
  INNER JOIN [dbo].[Message] m ON om.[MessageId] = m.[Id]
  -- ...joins to EntityType / SourceSystemEntityId...
ORDER BY o.[TimeStamp] DESC;     -- Type 3 = the exceptions
```

`CorruptionCheck` finds source IDs with **more than one active mapping** (`HAVING COUNT(*) > 1`, `State <> 3`) — the duplicates behind **`Synnduit.SynnduitException - An item with the same key has already been added`**. The usual root cause is **two processes running against the same StarBridge database at once** (the one-process rule, L1.5 / L3.7). Fix it by **restoring the most recent StarBridge backup** (restore locally first and re-run the query to confirm 0 rows come back), or — less ideal, since it loses history — using `Starbridge-Cleanup.sql` to deactivate the duplicate rows.

## When the destination record has vanished (NotFoundInDestinationSystem)
`Starbridge-NotFoundInDestination.sql` lists transactions with **Outcome 6 — NotFoundInDestinationSystem**: the source record still exists and StarBridge still holds an **active mapping** for it, but the **destination record is gone** — something removed it *outside* the sync, so the engine took no action. This **can't be auto-resolved**; a person has to decide *why* it was removed:

- **The removal was legitimate** (the record genuinely shouldn't exist) → remove the **source** record too, so both sides agree.
- **The removal was a mistake** → set the mapping's **`State` to `3` (Removed)** for that record **and all of its child mappings**. With the mapping gone, the next run sees the incoming record as **brand new** and re-inserts it into the destination.

Don't hand-edit `dbo.Mapping.State` with a raw `UPDATE` — go through the **`[dbo].[SetMappingState]`** stored procedure (this is what `Starbridge-Cleanup.sql` does), so the change is recorded as a proper operation:

```sql
DECLARE @RC int,
        @operationId uniqueidentifier = NEWID(),
        @timeStamp   datetimeoffset(7) = GETDATE();

EXECUTE @RC = [dbo].[SetMappingState]
     @mappingId    = 'AE2882C0-5375-44F8-BC9E-BB52FE9932A8'   -- the record's mapping (repeat for each child mapping)
    ,@operationId
    ,@timeStamp
    ,'3';                                                     -- 3 = Removed
```

## These get reported to you (SynnduitEmailNotification)
You don't have to hunt for the problem rows by hand. **`SynnduitEmailNotification`** — a scheduled support tool — queries every sync's StarBridge database for the transactions that need attention: **Exceptions and Rejections**, plus the **two outcomes that require manual intervention** — **NotFoundInDestinationSystem** (above) and **ReferredForManualDeduplication** (L1.11) — and **emails a report to the support team**. The diagnostic scripts here are what you run to investigate and fix a specific row once that report surfaces it.

## Why it matters
These scripts encode hard-won queries (the right joins across `Operation`, `Message`, `Mapping`, `EntityType`). Reaching for the right one turns a vague "the sync is broken" into a specific row with a specific message.

## Watch out for
- **Hand-writing the joins** when a script already does it — start from the folder.
- **Some scripts mutate data** — `Starbridge-Cleanup` (calls `[dbo].[SetMappingState]`), `…ManualDeduplication`, and remap scripts change StarBridge; read before you run and prefer the read-only ones for diagnosis.
- **Resetting a mapping to `State = 3` by hand** — go through `[dbo].[SetMappingState]` (via `Starbridge-Cleanup.sql`), *not* a raw `UPDATE`, and don't forget the **child mappings**; decide legit-vs-mistake *before* you change anything.

## You've got this when you can…
- Pick the right script for a symptom (exception text vs. "same key" corruption vs. not-found-in-destination vs. value change).
- Say where the message text lives (Operation/Message) and what the Type codes mean.
- Match the *same-key* corruption exception to `CorruptionCheck` (root cause: two processes on one StarBridge DB → restore the backup).
- Handle a NotFoundInDestination (Outcome 6): decide legit-vs-mistake, then either remove the source or `SetMappingState` the record + its children to `3` so it re-inserts — and know `SynnduitEmailNotification` emails the team these plus the manual-dedup queue.
