# L1.2 — Source vs. Destination

## In one line
A **source** is where data originates; a **destination** is where Synnduit makes it land — at CSSD **DDH** is both a destination for feeding systems and a source for consumers.

## The idea
Every sync has two ends:

- **Source** — the system of record where the data is *created and maintained*. At CSSD these include **HRAD** (PeopleSoft HR), **PowerSchool** (School and Student APIs), **ServiceNow**, and **JSON files**.
- **Destination** — the system the data is being kept in sync *into*.

Data flows **source → destination**. Synnduit reads from the source and writes to the destination; it never runs the other way for a given sync.

**Source and destination are roles a system plays *in a given sync*, not fixed labels.** The same system can be a destination in one sync and a source in another. At CSSD the **DDH (District Data Hub)** is the clearest example: it's a *hub*.

- **Inbound syncs** feed the DDH — the DDH is the **destination**. E.g. `Sync-SRC-DDH` pulls from HRAD, PowerSchool, ServiceNow, and JSON into the DDH.
- **Outbound syncs** export *out* of the DDH — the DDH is the **source**. E.g. `Sync-DDH-AD` pushes to on-prem Active Directory, `Sync-DDH-AAD` to Azure AD / Entra, and `Sync-DDH-SPO` to SharePoint.

The sync's name spells this out: **`Sync-<source>-<destination>`** — so `Sync-SRC-DDH` lands in the DDH, while `Sync-DDH-AAD` (Azure AD / Entra) and `Sync-DDH-SPO` (SharePoint) start *from* it.

Each sync is tracked by a **StarBridge database**, and one StarBridge database can hold the entities for more than one sync. From CSSD:

| StarBridge database | Source | Destination |
|---|---|---|
| `StarBridge-Hrad`   | HRAD (PeopleSoft HR), JSON, ServiceNow | DDH |
| `StarBridge-School` | PowerSchool (School API) | DDH |
| `StarBridge-Stdnt`  | PowerSchool (Student API) | DDH |
| `StarBridge-AD`     | DDH | Active Directory (on-prem) |
| `StarBridge-AD`     | Active Directory (on-prem) | HRAD |

`StarBridge-AD` (the `Sync-DDH-AD` integration) is the telling one: it tracks **two** syncs — **DDH → AD** and **AD → HRAD** — run separately but back to back, so data hops DDH → AD → HRAD through two one-directional syncs. On-prem Active Directory is the *destination* of the first and the *source* of the second — the same per-sync role rule as DDH.

Don't confuse it with **`Sync-DDH-AAD`**, a *separate* integration that tracks only the DDH → **Azure AD / Entra** flow. On-prem **AD** and **Azure AD (AAD / Entra)** are different destinations.

## Why it matters
"Source" and "destination" are the words every other concept is phrased in: a *feed* reads the **source**, a *sink* writes the **destination**, a *mapping* links a **source** ID to a **destination** ID. If you mix up which end is which, every later concept inverts.

## Watch out for
**Assuming a system has one fixed role — especially "DDH is always the destination."** It isn't: DDH is the destination for inbound syncs and the source for outbound ones (`Sync-DDH-AAD`, `Sync-DDH-SPO`). The role is set by the *direction of the sync you're looking at*. (And importance is irrelevant — the **source** is wherever data is *authored*: HR owns employee records, so HR is the source into DDH.)

## You've got this when you can…
- Define source (origin / system of record) and destination (where data lands) as **per-sync roles**.
- Explain why DDH is a **hub** — destination for inbound syncs, source for outbound ones — and read a `Sync-<source>-<destination>` name to tell which end is which.
- Classify real systems *for a given sync*: in `Sync-SRC-DDH`, PowerSchool/HRAD/ServiceNow are sources and DDH is the destination; in `Sync-DDH-AAD`, DDH is the source and Azure AD is the destination.
