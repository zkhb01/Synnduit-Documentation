# L0.E2 — POCOs & the nullable requirement

> **A real gotcha you *will* hit when adding entities.** The code compiles, runs, and looks
> like it works — but changes to certain fields silently stop being picked up. The cause is
> almost always a non-nullable POCO property.

## The generic part (brief)
A POCO is a plain class whose properties map to data columns; EF binds each column to a property. Nothing unusual — until you add Synnduit's rule on top.

## The Synnduit rule
**Synnduit requires entity (POCO) properties to be nullable.** Any source field whose type is a non-nullable value type — `int`, `bool`, `DateTime` — needs a nullable form so the engine can represent "no value" and diff correctly. A bare `public int Grade { get; set; }` is the bug.

There are two correct shapes:

**1. Make the property itself nullable** (simplest):
```csharp
[EntityProperty] public int? Grade { get; set; }       // int?  not int
```

**2. Keep a non-nullable property but give it a nullable proxy** (when the destination type must stay non-nullable):
```csharp
[NotMapped]
public int? NullableEnrollmentStatus { get; set; }      // the nullable proxy

[Required]
[EntityProperty(NullableProxyProperty = nameof(NullableEnrollmentStatus))]
public int EnrollmentStatus { get; set; }               // engine reads/writes via the proxy
```
Then in the feed's `Map`, you assign the incoming value to the **nullable** property; Synnduit moves it internally to the non-nullable one via the annotation:
```csharp
c.NullableEnrollmentStatus = reader.GetInt32(11);
```

## Why it breaks silently
With a plain non-nullable property, change detection misbehaves — *"it may seem that they work, but changes will come along that won't be picked up."* No exception, no compile error; the field just quietly stops syncing. When you apply the fix and re-run in test, the console works through the correction, showing **`NoChangesMerged`** entries as it reconciles the affected records.

## Special case: identifier fields (`SourceSystemIdentifier`)
The `SourceSystemEntityId` property itself is a `string` — a nullable reference type — so it does **not** need the nullable-proxy treatment; a plain getter/setter is fine. The wrinkle is that the source fields that *compose* the identifier are often non-nullable value types (e.g. `int StudentNumber`, `int PersonId`), and those fields do hit the same rule.

Rather than wire a `[NotMapped]` nullable proxy for every value-typed field that feeds the identifier, you can give `SourceSystemEntityId` a plain getter/setter and **build the string directly in the feed's `Map`**:

```csharp
[NotMapped]
[SourceSystemIdentifier]
public string SourceSystemEntityId { get; set; }
```
```csharp
public IEntityCollection<Guardian> LoadEntities()
{
    using var context = this.powerSchoolContextFactory.CreatePowerSchoolContext<Guardian>();
    return context.Entity(Map);
}

private void Map(OracleDataReader reader, Guardian c)
{
    c.StudentNumber    = reader.GetInt32(0);
    c.NullablePersonId = reader.GetInt32(1);
    c.FirstName        = reader.IsDBNull(3) ? null : reader.GetString(3).Trim();
    // …
    c.SourceSystemEntityId = string.Format("{0}_{1}", c.StudentNumber, c.NullablePersonId);
}
```

Because you assign the composed string yourself, the identifier value is set explicitly rather than diffed through the engine, so the nullable-proxy plumbing isn't needed on it. A source-system identifier is expected to always have a value (it's the key), so the silent change-detection failure mode doesn't arise the same way it does for ordinary fields.

## Multi-source POCOs: when null means "ignore" vs "set to null" (`ForceNullPropagation`)
A single POCO is often fed by **more than one source**, with each source providing only a **subset** of the properties. (In `Sync-SRC-DDH`, the `SchoolObjectModel` entities are fed by both **PowerSchool** and a **JSON** feed.) This adds a subtlety to what a `null` actually *means* — and it's another reason the properties are nullable.

**Default: a source's null on a property it doesn't provide is ignored — it is not a change.** If the JSON feed supplies only two of an entity's properties, the rest arrive as `null`, and the engine treats those nulls as *"not part of this sync,"* leaving the existing values untouched. That's what you want: one source shouldn't blank out fields owned by another source just because it doesn't carry them. (This is exactly the "no value vs. a real change" distinction that makes nullable properties necessary.)

**But sometimes the null *is* the change.** When a particular source *does* own a property and reports it empty, you want that null to **propagate** — overwrite the previous value with `null` — instead of being ignored. Mark the property with `[ForceNullPropagation(typeof(<SourceSystem>))]`:

```csharp
[EntityProperty]
[ForceNullPropagation(typeof(PowerSchool.PowerSchool))]
public int? DCID { get; set; }
```

Now, when **PowerSchool** feeds this entity and `DCID` comes in `null`, the engine applies it as a change (previous value → `null`) rather than skipping it.

**It's scoped to the named source only.** `ForceNullPropagation` names *one* source system. So PowerSchool's null on `DCID` propagates — but if the **JSON** feed also feeds this POCO and provides only a couple of properties, *its* nulls for `DCID` are still ignored, because the annotation doesn't name it. Each source keeps the "null = ignore" default except the one you explicitly opt in.

*Real code:* the `SchoolObjectModel` POCOs (e.g. `stdnt/Course.cs`, `School.cs`) carry `[ForceNullPropagation(typeof(PowerSchool.PowerSchool))]`; the JSON side is `Json/Feeds/SchoolSiteFeed.cs`, in `Sync-SRC-DDH`.

## Placement check
You add `public int Grade { get; set; }` to a POCO and runs start misbehaving (some changes never sync). What rule did you break, and what are the two fixes? (Properties must be nullable; either make it `int?`, or add a `[NotMapped]` nullable proxy wired with `[EntityProperty(NullableProxyProperty = ...)]`.)

## If this is shaky
Compare wrong (`public int Grade`) vs right (`public int? Grade`, or the proxy pattern). The engine needs the nullable distinction to tell "no value" apart from "zero/false/default" — without it, the diff can't see the change.
